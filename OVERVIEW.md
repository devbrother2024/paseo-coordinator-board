# Session coordinator board

The board groups existing Paseo sessions by project and shows which decisions need your attention. A coordinator can review recent conversations, assign work on this host, and report back. The interface supports Korean and English. Open **설정 → 보드 언어 → English** to switch this device to English.

## Install and choose projects

On the computer running your sessions, use **Paseo 0.16.2 or later**. In **Settings → Plugins**, turn on **Enable plugins**, paste this install ID into **Plugin source**, then select **Install plugin**. [Official plugin directory](https://paseo.sh/plugins/devbrother2024/coordinator-board)

```text
devbrother2024/coordinator-board
```

To install from the terminal on that host, run these commands and check that the board is `running`.

```sh
paseo plugin install devbrother2024/coordinator-board
paseo plugin ls coordinator-board
```

For a registry installation, preview a new reviewed release with `paseo plugin update coordinator-board --check`. Run `paseo plugin update coordinator-board` to review and apply the update.

**Git and ZIP installations.** On a host with Git, run `paseo plugin install git:devbrother2024/paseo-coordinator-board --ref main` for the default branch, or replace `main` with `v0.5.12` for the release featured in the video. A full commit SHA also works. For a ZIP, extract the package and run `paseo plugin install .` in the folder containing `paseo-plugin.json`. Keep that folder in place. [Paseo plugin guide](https://paseo.sh/docs/plugins)

Open the board from the sidebar and select the projects you want in your digest. In **Settings → Choose projects to manage**, the host marks temporary directories as **Temporary folder**. Projects with visible sessions remain available even if they are missing from the catalog. Projects with neither a catalog entry nor a visible session disappear from the board filters. Choose **Remove from list** to clear their entries from the managed list. To manage just one session from another project, open **Settings → Link a session from another project**. Search for the session, check its ID and source workspace, select a managed destination, then click **Link to this project**. The card appears once under its destination. The session keeps its original ID, workspace, files and conversation. **Unlink from project** removes the link. The card returns to its source project if that project is also managed.

In **Session progress**, choose **All running** to see running sessions across the selected projects and visible hosts, ordered by recent activity. Each row shows its project and host and opens the corresponding session. Choose **By project** for the kanban layout. Your device remembers the last view.

In the desktop app and on the web, press **⌘+Enter** on Mac or **Ctrl+Enter** on Windows and Linux to send from the current request, reply or question field. **Enter** inserts a line break. Hover over the send button or focus it with Tab to see the shortcut for your device.

**My decisions** shows overdue and urgent items first, followed by work waiting for a response or permission. Other items are ordered by deadline. Within a priority, the oldest known wait comes first. A card stays in place while you compose a reply or review a merge. Questions and explanations preserve line breaks and render Markdown lists, links, and inline code. Single tildes in date ranges or estimates remain visible. Use two tildes on each side for strikethrough, as in `~~text~~`.

After sending an answer, choose **Open receiving session** on the collapsed card to check the conversation. The sent reply stays in place as a collapsed card showing only **Reply sent**, the card title and the time sent (with the date when it was not today). **Show what was sent** opens the whole reply, the photo count, the receiving session and the first line of its follow-up. The card does not count as a decision and does not keep **Recent decision activity** from opening on its own when no decision is left. It moves to **Recent decision activity** on the refresh after the recipient's follow-up is verified or the card is taken down from the ledger, and at the latest 24 hours after sending. Other results, such as a merge, fold away after a few seconds. **Hide** clears a result at once. Expand **Recent decision activity** below **My decisions** for the exact message, time and recipient. When available, the history also links to the session that asked the question. An answer saved only on the board by an earlier version can link to its original session without implying delivery. Every sent answer is kept in one place, **Recent decision activity**, which follows the project filters above. An answer still waiting for a result also appears in that project’s **Awaiting review** column as a **Reply sent · awaiting result** card. The card shows the start of the message, when it was sent and how long ago, and a recipient chip that opens the session. It leaves the column, staying in Recent decision activity, once the recipient answers, the ledger card it answered is handled and taken off the ledger, or a day passes. Once the recipient’s follow-up is verified, or 24 hours after sending, the card leaves the kanban and stays only in the activity list. An answer that could not be sent stays in the same column for 24 hours as **Not sent**. Device-wide actions appear under **Host-wide**, which is hidden when it has no cards. A verified follow-up appears on the activity card, and the recipient chip opens the conversation. When the board cannot find the recipient session right now (for example an archived session, an earlier coordinator, or a session moved outside the managed projects), the activity card says **The recipient session can't be found on the board right now, so its result can't be checked.**

### Keep the coordinator conversation across board updates

Updating the board does not replace a running coordinator. A coordinator conversation remembers the definition of each board tool it has loaded. Claude Code stores the definitions in the conversation record and sends that copy on later requests and on resume, so reloading the session, reloading the plugin or restarting Paseo does not change them. The board therefore fixes the names and input formats of the coordinator tools as a numbered **contract**, and ships new features through two fixed tools.

- `read_board_guide` tells the conversation what the installed board accepts now, and what it added since the conversation received its tools: actions without a tool of their own, and input fields that the tool definitions do not list.
- `board_action` runs an action by name with the installed board's own input checks. Fields that the conversation's tool definitions lack go through this tool. The result and the permission checks are the same as calling the tool directly.

The existing tools keep their descriptions. An update that only rewords tool descriptions tells a running conversation nothing. When an action or an input field appears that only `board_action` can reach, the board adds a note to the coordinator's next board tool result, once, asking it to read the guide. The note goes once on a result that answers in plain text. A result that answers in JSON is left unchanged, and the note waits for the next plain-text result. Once the coordinator has read the guide, it uses the new features in that same conversation.

For a conversation that began before the contract existed, and for one that holds a contract the board no longer works with, the top of the board shows **The coordinator conversation uses board tools from before the update.** What it was doing keeps working. The fixes run from least to most context lost.

1. Leave it as it is. The next time the coordinator uses a board tool it is told to read the guide tool, and the notice goes away once it has. To do it now, choose **Open coordinator session** and type "Read the board guide tool" yourself.
2. If the notice stays, type `/compact` in the coordinator session yourself. The conversation keeps a summary, and the notice goes away when you refresh the board after the compaction ends. The board goes by the finished compaction it sees in the coordinator's timeline. A compacted conversation was seen to receive the tool definitions again with Claude Code 2.1.330; other versions may differ.
3. As a last resort, choose **Replace with a new session** or type `/clear` yourself. After a replacement, the new session follows its start instructions to read the previous coordinator's record and carry on (see **Handover after a replacement** below). `/clear` does not carry the earlier conversation over.

The board never types `/clear` or `/compact` for you, and never reloads the session. While Paseo restarts the plugin for a board update, the board tools drop out of the coordinator's tool list for a moment and then return. An error from a tool called in that moment comes from Paseo, and calling again shortly works. It stays quiet when the coordinator has not called a board tool yet and there is nothing to compare. The notice and the note are for coordinators that run on Claude Code. A session on a provider with another ID, such as a profile for a second account, counts when Claude Code runs it (the board reads the provider implementation name that Paseo records on the session). A coordinator on another provider receives the two tools as well, but the board cannot tell which definitions its conversation holds, so it shows nothing.

This relies on behavior observed with Claude Code 2.1.330: the definition of a loaded tool is fixed in the conversation, the client does not block a call that carries a field outside that definition, a tool added by an update is announced to an existing conversation, and compacting a conversation makes it receive the definitions again.

**Moving to contract 1.** A coordinator conversation that began on an earlier version shows the notice once. Leave it as in step 1: the two new tools are announced to that conversation, so it clears without a replacement, `/clear` or compaction. Later updates within the same contract need no replacement.

**When you change the plugin.** The names and input formats of the coordinator tools are tied to the contract number in `shared/coordinator-contract.ts`, and `test/coordinator-contract.test.ts` compares them with a snapshot. Add a new optional field to the tool's `accepts` and leave the tool's input format as it is. The field is then accepted through `board_action` and listed by `read_board_guide`.

### Handover after a replacement

A replacement coordinator starts without the old conversation. The confirmation box says so, and the board puts start instructions into the request that creates the new session. They open with **[Coordinator Board · Coordinator start]** to show they come from the board, and they carry the previous coordinator's session ID, a request to read its record with `read_board_conversation` and list the work in progress and the promises made before carrying on, and the number of open decisions and ledger cards. The new coordinator can read that record through the tool even when the previous coordinator sits outside the managed projects, as in the operations folder. Only the coordinator right before it can be read this way, and only while the session the board created by replacement is the coordinator. The board sends no separate message to the old or the new session. **Replace with a new session** in the board update notice follows the same flow.

The previous coordinator stays after a replacement. **Settings → Replace coordinator** shows a **Previous coordinator · Archive** row: press **Archive** once the new coordinator has read the record. While the old session is still running or waiting on a permission request, the button is off and the reason is shown. The row appears only for a coordinator the board created. Tidy up a session you designated yourself in Paseo.

A host administrator can put `coordinator-start.md` in the plugin data folder (`$PASEO_HOME/plugin-data/coordinator-board`) to add start instructions for every new coordinator. The board reads it each time it creates a coordinator and appends it to the start instructions, also on a first creation with no previous coordinator. A missing or empty file is ignored, only the first 4,000 characters are used, and control and bidirectional control characters other than line breaks and tabs are removed. For example:

```markdown
When you start, follow the START.md steps in the operations folder first.
```

## Work with a coordinator

The input grows and shrinks with its text. Past 60% of the window height it stops growing and scrolls inside. Request, reply, follow-up question and session note inputs all behave the same way.

Requests you send stay under **Sent requests** below the editor, up to the latest 20. Expand it to read the full text, the time, attached photos, and the delivery state (Delivery unconfirmed, Sent, or Delivered), and open the conversation with **Receiving coordinator session**. Delivered means the board found the message in the coordinator's conversation. Requests sent before a coordinator replacement show **Earlier receiving coordinator** instead. Photos stay viewable only while they are among the host's most recent 20 photo messages. The history is kept in the plugin's data on the host, and a request is still delivered when its history cannot be saved.

Click **Start with recommended settings** to create the coordinator, or select **Choose an existing coordinator session** in Settings. Before creating or replacing a coordinator, the board shows the model and tool permission mode. It prefers Auto mode for Claude Code and Auto-review for Codex when supported. OpenCode with Build mode and Copilot with Agent mode can serve as alternatives when their coordinator mode is available on the host. For other providers, you can designate an existing session with Paseo MCP.

Paseo pins a new coordinator workspace in the host’s sidebar by default. Turn this off in **Settings → Sidebar pinning**. Replacing the coordinator in the same workspace preserves its existing pin state. For an existing coordinator, click **Pin current coordinator workspace**.

To replace the coordinator with a different model, open **Settings → Replace coordinator**, click **Choose model**, pick one model, then click **Replace with this model**. The recommended model is listed first, and models that cannot run a coordinator are dimmed with the reason. The reasoning effort is preselected and can be changed. The picked model is saved as the default for later replacements (the first M candidate). Turn off **Use this model as the default for later replacements** to use it once. A model you pick takes precedence over usage-based routing.

On first creation or replacement from the legacy folder, the board names the project **Coordinator operations (do not delete)** or **코디네이터 운영 (삭제 금지)** based on the board language. Later replacements reuse that folder. Keep the active operations project even if it looks empty. If removing it disconnects the coordinator, use the board banner to replace the session.

When the coordinator cannot be reached, the top of the board says why. It tells apart a closed or failed session, an archived session or workspace, and an operating folder whose project was removed from Paseo. Removing a project in Paseo archives its workspace, so the coordinator stops receiving requests and replies. **Show recovery steps** names the folder to add again, and **Replace coordinator** opens the replacement box in place. Meanwhile, cards that reply to the coordinator show **Coordinator unreachable · See the notice above** and turn off sending. Your answer stays on the card; send it once the session is back. When the session that owns a ledger is not in the current session list, its **Operating coordinator** chip checks the session before opening it and shows the reason instead of an empty screen. The project list in **Settings** points out the coordinator's operating folder and warns that removing that project archives the coordinator with it.

On desktop or web, drop photos onto the coordinator request field or a decision reply, paste a screenshot, or choose the paperclip labeled **Add attachment**. Review the images, remove any you do not want to share, then choose **Send to coordinator**. You can send images with or without text. Attach up to four PNG, JPEG, or WebP images, up to 5 MiB each and 12 MiB combined. Photos over the limits, or wider or taller than 8000 px, are shrunk automatically before sending: the board scales down the long edge and saves the image again, and the preview shows the change (for example, 8.0 MiB → 2.4 MiB, 4032×3024 → 2560×1920). Saving again removes photo metadata such as the location, and an animated image keeps only its first frame. The original is neither sent nor kept. Photos over 50 MiB or 50 megapixels are not shrunk; the board asks you to choose a smaller one. If a file cannot be read or shrunk to fit, choose it again or dismiss the failed attachment before sending. Open the receiving session to see photos sent with a new request, reply, or question. Select a photo to enlarge it. The host keeps original images for the most recent 20 photo messages. On the native mobile app, open the coordinator session and attach photos in its conversation composer.

Use **Send to coordinator** to delegate work. Choose **Settings → Replace coordinator → Request digest** to ask the designated session to inspect the latest excerpts and record which decisions need a person. The board displays that evidence and refreshes while open. A new message can invalidate the coordinator's earlier judgment.

Each session decision has an **Open work session** chip beside the project. It opens the original conversation without sending a reply. The card leads with the question and one suggested reply. Open **Evidence and history** for the original text, the reason behind the suggestion, the session name and its host, and earlier questions and answers. The header shows only the project, how long the card has waited, and an **Open work session** chip, and a long explanation shows two lines before **More**. Use **Ask coordinator for a recommendation** to revisit an older card. If a necessary detail is missing, the card asks for that detail. Choose options directly on the card. When no suggested reply is available, type your own. Open evidence and history for context.

A worker asking “Which project does this session belong to?” can receive a verified answer from the designated coordinator during a requested digest. The project card shows a record of the response. **Settings → Automatic replies to factual questions** lets you turn this off for the host. Receiving a reply can start the worker's model and use its provider allowance. A decision such as deleting a work folder still requires the person responsible.

- **Reply to a session.** Each decision has its own card with one input. Edit the suggested reply in the input, or choose an option. A suggested reply is shown in full as the input grows, so you can send it right away. Only when the reply is too long and scrolls inside the input does **Confirm full reply** appear, and the send button turns on after you press it. Press **Send** below the input to send the displayed text to the recipient named beside the button.
- **Ask or request a change in the same input.** A card has no separate question box. Write an answer, a question to ask before deciding, or a change request in the same input and press **Send**. The board does not classify what you wrote. The session that takes it reads the card context, where `mayBe` (`decision`, `question`, `change-request`) says it may be any of the three. When you send a question, the card folds, and it opens as a new card when the receiving session asks back. The sent card stays in place as a folded **Sent** card. It closes when the session treats it as a decision and takes the card off the ledger, and it opens again with new content when the session asks back and raises the card again. A ledger card's folded card shows the first line of the session's answer and stays until the card is taken down or a day has passed. An approval request card (a tool run, for example) keeps **Ask a question**, because a question is all the board can send from it. To coordinate across tasks, choose **Ask coordinator to coordinate**, review the recipient, then use **Send request to coordinator**.
- **What the receiving session does.** For a decision, it acts and takes the card down. For a question or a change request, it answers or applies it, and if something is still yours to decide it raises the card again with new content (a ledger card records the exchange in `qa`). A card left unchanged does not come back on the board. A coordinator the board creates gets this in its charter. Tell a session you designated yourself, or a coordinator that was already running.
- **Answer a question or a plan on the board.** A session that stops to wait for you appears in **My decisions** as a **Requests awaiting a response** card. A question shows its original text and options: choose one, choose several when it says **Select all that apply**, or type your own answer under **Other**, then press **Submit answer**. In a single-choice question, an option and a typed answer replace each other. **Dismiss without answering** closes the question the way Paseo's own app does. A plan shows its opening lines and **View full plan**. The approve button says what approving changes (Claude Code: **Switch to auto-accept edits and implement**, Codex: **Leave plan mode and implement**). The first press asks you to confirm, and **Confirm** sends it. **Reject plan · Do not implement** leaves the session stopped. A choice that widens the permission mode further, such as implementing in the previous mode, is not offered on the board: use **Open work session**.
- **Respond to a tool or mode request.** For a shell command, the card shows the risk, working folder, command groups, and relevant file targets. It flags reads of sensitive files or paths outside the working folder. File reads show that symbolic link targets have not been verified. Remote work cards show the request title supplied by the provider. A request that mixes deletion and an unknown command shows both risks. **View full command** reveals the original command. File and MCP requests show the operation and target. Choose **Open work session** to approve or reject in Paseo's permission dialog. Questions and plans the board cannot handle also go to the work session. The board answers questions that Claude Code, Codex and OpenCode ask the user, and plans from Claude Code and Codex. A yes or no dialog from another provider or an extension can approve a tool run even though it looks like a question, so it stays in the work session. A question that asks for a hidden answer masks what you type, and the value is not kept on the card or in the record afterwards.
- **What the board sends.** The board answers only when you press a button. It does not choose an option or fill in a recommendation for you, and an answer holds only the options you chose and the text you typed. Just before sending, it checks that the request is still waiting. A request answered elsewhere or withdrawn by the session is not answered again and shows **Already handled**. Pressing twice sends one response. The result stays where the card was: **Sent** with what you sent, a failed send that you can retry on the card, or, when the session has not confirmed the response, **Check again** and **Open work session** without sending it twice. The host that runs the board plugin stores the response record. It starts empty before the first response. Reopening the board, including on another screen attached to the same host, keeps recorded requests from being answered again. If reading the record fails, you can still review requests on the board and answer in the work session. When the board is open for a host on another device, the answer goes to the session on that host. A delivery receipt confirms that the session received your message. Verify the result before recording completion.

A ledger card's header shows only the project, how long it has waited, the due date when there is one, and one chip. The chip opens the session that takes the reply: **Open coordinator** on a card the coordinator answers, **Open work session** on a card a work session answers. When that session has ended or cannot be verified, the card says why and the chip opens the session that can still be opened: the coordinator a redirected reply goes to, or a live work session on another host or project. The other session (source work session or operating coordinator) is under **Evidence and history**. A collapsed project preview shows both chips.

A ledger card spreads out only what it asks, what is recommended, and how to answer. The request shows two lines and opens with **More**. The recommendation shows one line, and its full text is under **Evidence and history**. The ledger's steps (`steps`) always show as a numbered list right under the recommendation, so a recommendation such as "check in the order below" has its order on the card. More than five steps show the first three and **Show all n steps**. Evidence, risks, earlier questions and answers, and earlier replies are under **Evidence and history**. The card has one input and one **Send** button, and the recipient is named beside the button.

A card with two or more questions opens straight on its first unanswered question, with no button to press first, and shows one question at a time so the next card stays in view. Progress dots that jump to a question and the heading **Question 3 of 10** sit above the question. Recommendations show as a **Recommended** mark beside an option and in the card's recommendation line, and you choose each question yourself. Choosing an option in a single-choice question moves to the next one. A multi-choice question or a written answer moves on with **Next**, and **Previous** goes back. The field for your own words opens with **Something else (write it)**, and each question's photos and **Skip this question** are under its **More**. After the last question a summary list such as "Q1 A · 20 photos, 100 MiB" shows. Tap a summary line to return to that question. The card's input and **Send** stay under the questions the whole time: write a question or a change request there and it goes out on its own, without answering every question. While that input is empty, every question still has to be answered or skipped before sending. The message sent is unchanged, and a draft survives moving between questions and list refreshes. A card with one question shows its options and field together as before. A card that cannot take a reply shows all its questions at once, without steps. Claude and Codex workers and coordinators can receive card replies during their current turn and continue working. The board checks an open conversation card against the latest question before sending. If the conversation has changed, review the latest card.

For providers without mid-turn input, the board queues the reply and photos. Set `"deliverWhenIdle": true` on a ledger card or put `deliverWhenIdle: true` on a separate line in a conversation question to wait until the turn ends. Only the JSON boolean `true` opts a ledger card in. A string such as `"true"` leaves the card available. A conversation marker with different capitalization or a trailing period is also ignored. In these cases a session that accepts mid-turn input receives the reply immediately. The board holds delivery during permission requests. The queue survives closing the board and checks the question and recipient again before sending.

When the provider lacks mid-turn input or the wait reaches 10 minutes, choose **Request a parallel session**. You can change the wait in board settings. This pauses the original reply and asks the coordinator to check whether the work is independent. Choose **Cancel queued reply** if another session picked up the work, or **Resume original reply** if the original session should handle it. Once the original session closes or is archived, you can only cancel the queued reply.

A ledger's example reply appears only as placeholder text. Tap the **Suggested · …** chip under the field to insert the recommended reply and edit it: the first short one of the ledger's reply (`recommendedReply`), its example reply (`howToAnswer`, the sentence to send after following the recommendation), and the first recommended line. A recommendation phrased as an instruction ("Disconnect the remote desktop") is therefore replaced by the example reply ("Disconnected the remote desktop") when the ledger has one. An example reply that lists choices ("A / B") or leaves blanks (`<time>`) is skipped. When none exists or all are long, the chip is hidden, and a personal check suggests **I checked this** instead. On a card with options, choose the option marked **Recommended** yourself. When the work session has ended or belongs to another project or host, the card says so and offers **Send to ledger owner instead**. On a card without a ledger owner, the button reads **Send to coordinator instead** and goes to the board coordinator. The button takes the place of the send button, and the board refuses that redirect once the original session can take the reply again. A card with no session to take the reply and no fallback explains why and shows no reply field. To reply directly to a session in another project, link it under **Settings → Link a session from another project**.

Projects that open the same folder, such as two Paseo projects whose paths differ only in letter case, count as one project. A work session in either one takes replies directly without a link, and the card's session chip opens it. The board asks the disk whether two roots are the same folder. On a case-sensitive disk, paths that differ only in letter case are different folders, and a folder that only shares a name is a different project. Both projects must be managed on the board. This is the same check that joins those projects into one filter, and a disk that answers slowly or cannot be read keeps the two projects separate. If the disk answers slowly just as a reply goes out, the board asks you to try again in a moment instead of reporting the session missing.

A rejected reply names its reason and keeps your text. If only the evidence, risks, urgency, example reply, short recommended reply, or history changed, you can send the same text again. A changed title, request, recommendation, question, option detail, or recipient needs a fresh look first. Text written before a card gained questions stays visible and is sent with your answers unless you edit it or choose **Remove this reply**. A photo whose question no longer exists must be removed before sending. Retrying an unconfirmed reply only checks the history of the session that took it, even after the card changes, moves to another work session, or gets a new ledger owner. Nothing new goes out on that card until the reply is confirmed, 10 minutes pass, or the session that took it is deleted or archived. After that, the changed card takes a new reply and the earlier one stays unconfirmed. If that reply turns out to have been delivered, the changed card stays open and says so. After two rejections for the same reason, the card points you to the session instead of another refresh.

Decision replies include the original project, session when known, card, question, and revision alongside the answer. When a ledger card has an answer lead (`answerLead`), a reply to its questions opens with that line so the recipient can tell what the answers decide. The line appears above the send button, and **Remove first line** leaves it out. A reply written only in the free field goes out as written. To report a personal check, tap the **Suggested · I checked this** chip and send it to the coordinator, which takes the card down. A card you no longer need is closed the same way, by replying "Not needed, close it" to the session that takes it. The board has no button that closes a card without sending. During a digest, the coordinator can archive a verified merge-only record or a completed source-session check. After you send a reply or merge a PR, the result stays where you acted in **My decisions** for a few seconds, then folds into **Recent decision activity**. **Hide** clears it at once. A reply that could not be sent stays until you hide it, since its text is kept nowhere else.

Open Settings to compare remaining quota bars and reset times by account. Each reset time also shows the time left from now (for example **5d 2h left**, hours and minutes within the last day, **resets soon** within the last minute), updated every minute while Settings is open. Credits without a reported limit show a balance. A host can supply dated, display-only readings for providers missing usage through an optional account-usage.json file. Each report there can also list usage reset passes a subscription grants in an optional `resetPasses` field, for example `"resetPasses":[{"id":"weekly","label":"Weekly reset","left":2,"expiresAt":["2026-12-11T07:00:00Z"],"note":"Restores the weekly limit"}]`. Each pass has an `id` and `label` (up to 64 characters), a whole number `left` (0 or more), a list of up to 16 `expiresAt` times, and an optional short `note` (up to 200 characters; left out when empty or only spaces). Malformed passes are dropped and the rest of the report is kept. The account card shows how many of each pass are left with the nearest expiry still ahead and the time until it, and a pass with none left reads **None** in muted text. The count follows the file, and passed expiry dates are only left out of the display. For a provider Paseo measures itself, a report with the same `providerId` adds only its reset passes and leaves Paseo's windows and balances as they are. Where a provider has one account, passes attach to it whatever its `label`; where it has several, they attach only to the account whose `label` matches exactly. Passes added this way show the host report's `fetchedAt` on their own line, and turn muted as **last known** once it is older than the limit used for account readings. Host reports, reset passes included, are never used for automatic assignment. Each account card has a **Used for automatic assignment** switch. Turn it off and the board assigns no work to that account: it is left out of the recommendation and of usage-based selection, and skipped where a custom list still holds it. The board assigns to providers, so accounts under one provider turn on and off together. The **Order by remaining usage** switch above the cards compares fresh, matching quota windows for the accounts that are on, and a grade decided this way is marked **By usage** in the routing table. Changing such a grade saves it as custom with the model in use kept first, and the row says usage-based selection no longer applies to it. An explicitly saved model order takes precedence.

## GitHub pull requests

The sidebar count combines session questions, pull requests ready for review, and decisions from configured project records. Entries referring to the same pull request or verified session question appear together. A pull request shared by several managed projects counts once. Choose **Merge on board** to review the repository, branches, commit, and allowed merge methods. Confirm to merge with the host’s authenticated GitHub account. Select the underlined repository and PR number at the top of the card to read the diff on GitHub. A changed commit or failed requirement requires another review. Drafts and pull requests waiting for checks appear in project progress. While GitHub is still computing whether a pull request can merge, the card says so and the board asks GitHub about that pull request alone, so the state settles quickly. **Status unknown** appears when the board could not read or could not judge the GitHub state, together with the reason: a failed lookup, mergeability still not worked out, a check without a result, an unrecognized review or merge state, or no linked repository. When a ledger card names the pull request's work session (`agentId`, `sessionHost`), the pull request row shows that session too. A session on another host appears only after that host confirms it. A ledger merge card stays out of **My decisions** until GitHub confirms its pull request is ready. Until then the pull request row in project progress shows the status and the reason. Once confirmed, the card moves to My decisions with its description and questions. When another merge on the board moves the base branch of the same repository, the board reads an open merge preview again in place. You still press merge again on the new preview. When new commits stop the merge, choose **Check the latest again** in the same card. Once the board confirms that the pull request of a ledger merge card merged or closed on GitHub, the card leaves **My decisions** at once and stays in **Recent decision activity** as **Merged · Waiting for the ledger to clear it** (or **Closed without merging**). The board does not edit the ledger file; the coordinator clears it. The time on that entry is the actual merge time when the board merged it, and otherwise the time the board confirmed the merge or close (**Board confirmed**). If the board cannot confirm the state, the card stays. The board reads open pull requests with the host’s authenticated GitHub CLI. In **Settings → GitHub repositories by project**, choose automatic detection, enter an explicit repository, or turn off lookup for a project.

Approval, question, and check cards from a ledger show a GitHub link below the title when the ledger provides a repository and PR number. The link includes the PR state when it is available. A bare number such as `#42` in the title or body links to the PR in the ledger’s repository. When the name right before a number (a Korean particle after it is ignored) or in brackets right after it is a repository or project the board knows (`alpha-web #12`, `#12 (alpha-web)`), the number links to that repository; in a table, the cell under a "Repository" header decides. `owner/repo#12` links when the board knows that repository. The board knows repositories from the per-project GitHub repository settings, ledgers, the open pull request list, and merge history. A number beside an unknown name, or a name that matches more than one repository, stays unlinked. A number with no name beside it uses the ledger repository only when the whole text names no other repository. To avoid opening the wrong PR the board does not guess from the rest of a sentence, so a plain word before a number, as in `Closes #12`, can leave it unlinked.

With a designated coordinator, a pull request that GitHub can merge reaches **My decisions** only after the coordinator checks it. During a digest, the coordinator reviews each open pull request (whether the work is finished, review comments are addressed and checks pass on that commit) and records a verdict bound to its current head commit. A merge card appears for a ready verdict or a merge request the coordinator put in its ledger. A ledger merge request does not raise the card while a verdict on an earlier commit remains or the current commit has a verdict other than ready. Other pull requests stay in project progress as **Awaiting coordinator review**, **Needs changes: reason**, **Work in progress** or **Blocked: reason**. New commits after the verdict show **New commits · Needs another review**, and the merge preview stops if the head differs from the commit the board showed. While a work session linked to the pull request (a session on its branch, the session the coordinator named, or the session behind a ledger merge request) is running on that pull request's branch, the merge card stays out of **My decisions** and waits in the **In progress** lane as **Work session running · Moves to a merge card when it finishes**. Once the session rests, the next refresh raises the merge card. When that session has moved on to the next piece of work on another branch, the merge card appears with one line: **The work session is busy with other work.** When the board cannot tell the session's branch or cannot read the host it runs on, the merge card shows a warning and **Merge on board** asks once more. To raise merge cards from GitHub status alone, turn off **Settings → Merge cards only for PRs the coordinator checked**. While no coordinator is designated, GitHub status alone decides, except that a verdict other than ready on the current commit keeps the pull request in project progress.

A merge card has an input and **Send change request** under **Merge on board**. When the verdict says ready but you see something to fix or ask, write it there and send it; photos can be attached. It goes to the work session the coordinator named as the PR's owner. When that session is missing, archived, ended, failed, waiting on a permission request, or on another device, the coordinator takes it. The recipient is named beside the button. A recipient in the middle of a turn follows the same rule as card replies: a Claude or Codex session takes the request in its current turn, and any other provider leaves it **Queued** on the pull request row until the session rests. While it waits, **Cancel queued reply** removes the request and brings the merge card back, and once the wait you set has passed or the provider cannot take mid-turn input, **Request a parallel session** asks the coordinator to look. A session waiting on a permission request or in an error state is not sent to, and the card says so. With no work session and no coordinator to take it, the card says why instead of showing the input.

Sending takes that merge card down at once and leaves a folded **Change request sent** card in its place. The pull request shows in project progress as **Change request sent · Waiting for a new commit**, and a ledger merge request waits with that row. A new commit expires the earlier verdict, so the pull request goes through the coordinator's review again before a new merge card appears. A commit you asked to change is released only by a new commit or by you pressing **Reopen merge card** on the pull request row. A coordinator recording the same commit as ready again does not bring the merge card back. When nothing in the code changes, press **Reopen merge card**, which sends nothing. The board does not merge a commit you asked to change: pressing **Merge on board** on an old merge card left on another screen is refused, and the card points to **Reopen merge card**. A request whose delivery could not be confirmed may have arrived, so it takes the merge card down the same way and the row shows **Checking whether the change request arrived**. It turns to sent once the board finds it in the recipient's conversation, and **Reopen merge card** lets you send again. A merge made on GitHub is not stopped.

When GitHub confirms a merge performed on the board, the board sends the PR link and the available merge commit to the responsible coordinator. This can start a model turn to assess follow-up work. The board queues the notification while the recipient is busy and shows delivery status separately from the merge result. Viewing a PR that was already merged does not start a turn.

## Models, hosts and tools

In **Settings → Model routing**, one table shows grades A through D and the coordinator: what each grade is for, the model in use, whether it is recommended or custom, and how many fallbacks stand behind it. Click **Change** on a row to open its candidates in priority order. Use **+ Add candidate** to pick a model and add it as priority 1 or as a fallback, then move candidates up, remove them, or change the reasoning effort on each row. Every change is saved at once, and **Undo** returns to the previous state for a few seconds. The picker groups models by provider with search, dims models the grade cannot use and says why, and offers only the efforts a model supports. When the first candidate cannot be used, its row gives the reason and the fallback in use. Providers discovered on the active host are included by default. Turn one off with its account card's switch under **Accounts and usage** and turn it back on later. With only Codex, grades use the connected Codex models. Without an available Claude Code or Codex model, ordinary higher-grade tasks can use another connected provider. If a saved list has no available candidate, edit it or choose **Back to recommended**. Session cards show the provider and model reported by Paseo.

**Settings → Paseo hosts** shows the app’s connections for browsing sessions and the board daemon’s connections for assigning work. Use **Hide** and **Show** to control which hosts appear in the session browser and the remote running list. Open **Register an assignment host** for the one-time registration command and refresh the assignment connections afterward. The coordinator can then assign work while the board screen is closed. Connect the destination in the app too if you want to open its sessions directly. [Paseo host registration guide](https://paseo.sh/docs/cli#connected-hosts)

Prepare the project and open a Paseo workspace on each intended host. The board pairs existing projects by repository address or a unique project name when the address is unavailable. Use **Assignment settings** to choose a project pair, override the detected OS, disable assignments to a host, or set a concurrent session limit. Under **Assignment options**, you can specify an OS or a host. For work that can run on any OS, the board chooses the eligible host with the fewest active sessions and prefers the board host when the counts match. When the requested destination is unavailable, the board shows the reason. Remote workers appear under the same managed project with the reason for placement, and their permission requests and questions appear in the board’s decisions and digest.

A coordinator with its own router can set `job.routeSource` to `"coordinator"` in `assign_board_worker` and pass its chosen provider, model and reasoning effort. The board checks the destination catalog, provider exclusions, required hooks and worker permission mode. The board applies its grade-based routes and usage ranking only when this field is omitted.

The board retains up to 256 multi-host assignment records for 30 days. It removes records for unmanaged projects and for delivered assignments whose sessions are archived or deleted. When a new assignment needs space, the board removes the oldest delivered records for idle or closed sessions with no open decision or pending reply. Unconfirmed records also expire 30 days after creation.

After cleanup, the board keeps the session ID, host ID, and request key for up to 1,024 assignments for 30 days. A retry with the same key stays on the original host and fails if that host is offline. When no record remains, the board checks other connected hosts for the same session before creating one.

The coordinator uses `read_board_conversation` to read managed sessions (the list also shows each resting session's lane, when it started resting, hours waited and whether it is not yet handled by the coordinator) and `classify_board_conversation` to record a judgment tied to the current evidence. It uses `plan_board_assignment` and `assign_board_worker` to delegate work. When a board update adds an action or a field that the conversation's tool definitions lack, `read_board_guide` lists it and `board_action` runs it. A worker on the board host with reporting enabled can post a question or a result to its own card with `report_to_board`. These tools require Paseo MCP integration in the session's provider.

The host stores project selections, session links, judgments, delivery receipts and notes in its local plugin data. Opening the board does not start a model. When you send a message, the receiving session uses its provider under your existing plan. [한국어 사용 안내](README.md) · [MIT license](LICENSE) · [Third-party notices](THIRD_PARTY_NOTICES.md)


## Kanban and decision records

Project progress shows occupied lanes side by side on desktop and stacked on a phone. Session rows show their execution host. Connected, visible remote hosts can show running sessions when their project ID or repository identifies a managed project. Opening a remote session takes you to that host.

Session cards in **Awaiting review** are sessions that finished and are resting (the same column also holds pull requests with something to fix and **Reply sent** cards waiting for a result). Session cards never move to **My decisions** on their own. If a decision is needed, the coordinator raises a decision card. Cards in Awaiting review and Idle show how long the session has rested ("Waiting 3 h", "Waiting 2 days") and a one-line summary of its last message. The summary prefers a sentence that says why it stopped, such as "stopped", "waiting", "정지" or "기다린다", and otherwise uses the last paragraph. Expand an Awaiting review card to read the full last message.

When a coordinator is assigned and a session in Awaiting review has rested longer than the threshold (12 hours by default) with no open ledger card pointing at it and no message or assessment from the coordinator on its current excerpt, the card shows **Not handled by coordinator**. Press it for an explanation. Choose 6, 12, 24 or 48 hours in **Settings → Not handled by coordinator**. Without a coordinator, the flag never appears. It also stays off for sessions whose conversation the board could not read (a session with a last error, or a failed read). When you request a digest, the coordinator reads and classifies flagged sessions first. The flag clears once the session is classified.

Project owners can supply independent records in `tracked-decisions.json` in the plugin data directory, or link existing project ledgers through `tracked-sources.json`. This retains manual checks, multiple questions tied to one session, and release decisions that include a second question. Recording a choice closes that version of the record. Sending a message and confirming a GitHub merge are separate actions. [Configuration example](README.md#프로젝트별-칸반과-결정-원장)

In a linked ledger card, `agentId` identifies the work session. The optional `sessionHost` accepts a host `serverId` or the name registered in the app. Names are case-insensitive. When the host is omitted, the board checks the current host first, then looks for the same session ID on visible online hosts. The work session chip opens the conversation on its host.

In a linked project ledger, each `questions[].options[]` entry needs a choice identifier `key` and readable `text`. Optional `does`, `pros`, and `cons` take a string or array of strings. Use `note` for a short explanation and `recommended` for a boolean recommendation flag. A card without questions can carry a short reply for the suggestion chip in `recommendedReply` (a string). Without one, a short `howToAnswer` is used, then the first recommended line. Changing only that field does not make a new revision, so an answered card does not reopen. The board ignores extra fields such as `label` and `detail`. When `label` is present and the required `text` is missing, the warning explains which field to use.

Valid cards from readable ledgers stay on the board. A small mark beside the **My decisions** count says some records could not be read. Open its **Details** to expand a warning to see the source and field paths for a rejected card. If the file cannot be opened or does not contain a readable JSON `items` array, the warning identifies the ledger source.

If a ledger’s reply or question history cannot be read, its cards are read-only. Reply delivery and local recording are available again once the history can be read.

Below the board title, one row shows **All**, any selected filters, and projects with pending decisions, in descending order until the row fills. Unselected projects with zero decisions appear when expanded. Scroll horizontally on narrow screens if the selected filters fill the row. Use **+N** on the right to expand the list, and **Collapse** in the same place to return to one row. The button is hidden when all filters fit. Your device remembers the view. Managed projects using the same folder share one filter. Separate folders with the same title show a path suffix. Counts show pending decisions, with shared pull requests counted once. Select any combination of filters to update **My decisions**, **Recent decision activity**, and **Session progress** together. Press a selected filter to clear it, or choose **All** to reset.

**My decisions** shows the last digest time when available. **Refresh digest** appears after three hours if a new, unclassified work session question has arrived since that digest. After the request is accepted, the button shows **Requested** until the next digest completes.

A merge decision retains its GitHub link after the PR closes. Its pull request row shows the state read from GitHub (such as **Merged**) right away. Moving the card to recent activity waits for the board's own merge or close check, which can take until the next refresh. A follow-up question on a merged PR sends only the answer to that question. A verified workspace match adds a session chip with its host and status to the PR card. A ledger card's chip opens the session that takes its reply, and its collapsed project preview shows both the operating coordinator and the source work session. For a tracked decision, select the named recipient to send your answer.

When a work session stops on a bare label such as “Shall I go with (b)?”, the card shows the explanation the session wrote before asking and what each option means. **Options** stays open under the question and lists each label's definition, found in that message or earlier ones. **Earlier in the message** shows the first four lines of the text right before the question; select **Show more** to read the rest. If those lines end in a table, its header shows with the first row; if they end on a heading, the first line under it shows too. Cards under **Session progress** show the same. If the session history does not explain a label, the card says so, and **Ask the session to explain the options** fills the card's input with a request to explain every option, its pros and cons, and the recommendation in one message. A ledger or coordinator card that names options it does not explain, or that points you to the session for details, shows the same notice with **Ask coordinator to complete the card**. Both buttons only fill the input. Nothing is sent until you review the text and send it.

Question cards the board finds in a work session's last message follow the same order as ledger cards: the header line (project, time waited, **Open work session**), the sentence that asks (up to two lines), the text after it, then **Earlier in the message**. A question inside quotes ("…", “…”, '…', 「…」, 『…』) or inline code (`…`) is not treated as a request, so a message that only quotes a question or shows a phrase as an example does not become a question card. A numbered or bulleted line that asks keeps its number and its list together on the card. A line that opens with ``` and has no closing ``` is shown as plain text, so it does not turn the rest of the message into one code block. A message also counts as a request when it opens with a decision heading (Korean 결정할 것:, "Decision needed:", "This needs your decision"), tells you how to answer with a quoted reply (Reply "merge" or "keep"), or says it will act once it hears back, even without a question mark or "please choose". When answer options follow the heading as a bullet list, the card starts at the heading line. "No decision needed", "let me know if you need an answer" and "applied after your answer" do not make a card.

A question the board finds in a session's conversation stays as a card until something shows it was handled. The board records the questions it finds in this host's settings, so the card stays even when the question scrolls out of the recent conversation, or the session is working or has ended. The card closes when one of these happens:

- A reply you sent from that card on the board arrived in the session.
- The session says it handled it, on its own line in a later message: `결정 반영: <요약>`, `Decision applied: <summary>`, or, when it moved the question to the ledger, `질문은 카드 <name>로 옮김` or `question moved to card <name>`. Lines inside code blocks or quotes do not count.
- The coordinator relayed your answer to the session with its source, and an answer line in that message (`Q1 · question: A · text`, `Q1 A`, …) matches an option of the card. For example, you answered a ledger card and the coordinator passed your answer on. A message from any other session is not evidence, and an answer that fits two or more open questions closes none.
- The same question moved to a ledger card and that ledger card was resolved. Besides a card the coordinator linked with `sessionMatch`, a ledger card for the same session (`sessionId`) with the same question words also takes the question; while it is open only the ledger card shows it. While the ledger card is open, it shows the question, and if it leaves the ledger without a resolution the question returns to its conversation card.
- The coordinator reads the session's record, judges that it was handled, and records that with evidence (below).
- What you wrote to the session yourself matches an option or the recommended reply of the card (for example `Q1 A`, `(b)`, an option's text, or the recommended reply). A question block with several questions needs every question answered, and an answer that fits two or more open questions closes none of them.

These are not evidence, so the board does not close the card on its own: you write something else to the session, the session keeps writing without a question, or the session has several open questions. For such a question the board tells the coordinator once, with a notice that carries the board as its source (`[Coordinator Board · 판단 필요 / Judgment needed]`). The coordinator reads the session's record and records "handled" (evidence required) or "needed" with the `judge_open_question` action of `board_action`, after finding the question key with `list_open_questions` (it lists them even while the session works), the evidence naming the message, reply or card. Questions of a session that ended are judged the same way. Handled closes the card, and the coordinator's evidence shows in recent decisions. When it finds no evidence the verdict is needed, and the card says what to do as "Needs your decision · <todo>" (the question's first line when the coordinator gives no todo). While a judgment is pending the card's question shows as a normal decision card, and other questions of the same session show with it under "Other decisions in this session", judged or not (past 10 they fold under "n more", and opening shows them all). If no judgment comes within 30 minutes, the board sends a new "Still not judged" notice, then waits twice as long each time up to 8 hours (it does not resend a notice that failed). Notices go one message at a time, at least 5 minutes apart, and the 20 questions in a message are taken in turn from each session, at most 5 from one session and one message per session every 30 minutes. Messages from other sessions, board notices and heartbeats do not count as your answer. Before a judgment the card looks like any other decision card however old it is, and the header shows how long it has waited. It never dims or leaves for its age. While the session works, it still shows as running and the card stays in My decisions. If the session ends, is archived, or the board cannot find it, the card stays and says that no reply can be sent in place of the reply box. To close it yourself, use **Close as handled yourself** under the card's **Evidence and history** (recorded on this host's board only, nothing is sent to the session).

To ask before deciding, write the question in the card's input, attach a screenshot if you need one, and press **Send**. Exchanges from the earlier **Ask a question** box stay under **Questions and answers** in **Evidence and history**.

### A question block for options

When a session ends its message with a `board-question` code block, the board draws its questions and options like a ledger card. Choosing an option fills the card's input with a line such as `Q1 · Where should the cache live?: A · Memory`. A recommended option carries a **Recommended** mark, and **Use recommendation** puts `recommendedReply` into the input. The board reads what is chosen from the text in the input, so editing or deleting a line changes the highlight too. Nothing is sent until you press **Send**. An option's `does`, `pros` and `cons` show when **Evidence and history** is open.

````markdown
I compared two places. Please choose one.

```board-question
{
  "questions": [
    {
      "id": "Q1",
      "text": "Where should the cache live?",
      "options": [
        { "key": "A", "text": "Memory", "does": "Keeps it in the process", "pros": "Fast", "cons": "Lost on restart", "recommended": true },
        { "key": "B", "text": "Disk", "does": "Keeps it in a file" }
      ]
    }
  ],
  "recommend": "A. Memory is enough at this size.",
  "recommendedReply": "Go with A for Q1."
}
```
````

| Field | Meaning | Limit |
|---|---|---|
| `questions` | The questions (required) | 1 to 8 |
| `questions[].text` | The question (required) | 500 characters |
| `questions[].id` | A short label used in the reply | 24 characters |
| `questions[].multi` | `true` lets the person choose several | |
| `questions[].options` | The options. Leave empty for a question answered in words | up to 8 |
| `options[].key`, `options[].text` | The option's label and text (required) | 16 and 300 characters |
| `options[].does`, `pros`, `cons` | What choosing it does, its benefits, its trade-offs | 400 characters each |
| `options[].recommended` | Marks a recommended option | |
| `recommend` | One line of recommendation | 600 characters |
| `recommendedReply` | A reply the person can send as it is | 2,000 characters |

- The block must be the last thing in the message, and its body may hold up to 12,000 characters. A block followed by other text is not read. A block quoted earlier in the message stays as text, and a block inside another code block or an indented one is not read as a question either.
- If the body is not JSON, goes over a limit, leaves a required value empty, repeats a `key` within a question, or repeats a question label (`id · text`), the whole block is ignored and the message shows as a text card, as before.
- Unknown fields are ignored. Control characters are removed before the block is shown.
- A message with a block becomes a decision card even when no sentence before it asks. The first question is the title.
- A question written without a block still shows as a text card, and the coordinator can move its options into a ledger card.

# Intent: 보드를 업데이트해도 운영 중인 코디네이터 대화를 그대로 쓴다

생성: 2026-11-25 유지관리자 요청
승인: 2026-11-25 유지관리자(세션)
상태: 구현됨 (PR #62)

## 문제

보드를 업데이트할 때마다 화면 맨 위에 "코디네이터가 보드 업데이트 전의 도구 정의를 기억하고 있어 새 기능을 쓰지 못합니다"가 뜨고, 해결책으로 코디네이터 교체와 `/clear`만 제시된다. 둘 다 운영 중인 대화의 맥락을 버린다. 하루에 한 번 교체한 뒤에도 다음 업데이트에서 다시 떴다.

원인은 두 가지다.

- 도구 정의 지문이 코디네이터 도구의 이름, 제목, 설명, 입력 형식 전체로 만들어진다. 설명 한 줄이나 선택 항목 하나만 바뀌어도 지문이 달라져 안내가 뜬다.
- 새 기능을 내는 길이 "도구 정의를 고친다" 하나뿐이다. 이미 도구를 받은 대화는 옛 정의를 계속 쓰므로, 새 선택 항목을 보낼 수 없다고 판단한다. 실제로 배정 도구에 경로 출처 항목이 더해졌을 때 운영 중인 코디네이터가 그 항목을 넘길 수 없다고 보고했다.

## 확인한 사실

시험용 MCP 서버 하나를 두고 도구 정의를 바꿔 가며 Claude Code 2.1.330으로 직접 확인했다. 문서로 보장된 동작이 아니라 이 버전에서 본 동작이다.

| 확인한 것 | 결과 |
|---|---|
| 대화가 이미 불러온 도구 | 정의가 대화 기록에 저장된다. 서버 정의를 바꾸고 대화를 이어받아도 옛 정의를 쓴다 |
| 옛 정의에 없는 항목을 넣은 호출 | 클라이언트가 막지 않는다. 옛 정의가 추가 항목을 금지해도 호출이 서버까지 가고, 검사는 서버가 지금 정의로 한다 |
| 업데이트로 새로 생긴 도구 | 기존 대화에 새로 쓸 수 있는 도구로 알려지고, 불러오면 지금 정의를 받는다. 교체나 압축이 필요 없다 |
| 대화 압축(`/compact`) | 대화 ID는 그대로다. 압축 뒤에는 도구를 다시 불러오며 그때 지금 정의를 받는다 |

따라서 운영 대화가 못 쓰는 것은 "이미 불러온 도구에 나중에 더해진 항목" 하나이고, 그 이유는 클라이언트의 차단이 아니라 대화가 가진 정의에 그 항목이 없다는 점이다.

## 바뀐 뒤의 모습

- 코디네이터 도구의 이름과 입력 형식이 번호가 붙은 계약으로 고정된다. 설명 문구를 고쳐도 운영 대화에는 아무 안내가 뜨지 않는다.
- 새 기능은 고정된 도구 두 개를 거쳐 나간다. `read_board_guide`는 지금 설치된 보드가 받는 기능과 입력을 알려 주고, `board_action`은 이름으로 고른 기능을 지금 설치된 보드의 검사로 실행한다. 두 도구의 입력은 열려 있어서 대화가 가진 정의를 바꾸지 않고도 새 항목을 보낼 수 있다.
- 기존 도구의 설명은 그대로 둔다. 새 대화가 규칙을 놓치지 않게 하기 위해서다. 안내 도구는 대화가 도구를 받은 뒤 더해진 것(도구 정의 없이 낸 기능, 도구 정의에 없는 입력 항목)을 맡는다. 그런 것이 생기면 보드가 그 대화에 "안내를 읽으라"고 한 번 알린다.
- 이번 업데이트를 받은 운영 대화는 사람이 아무것도 하지 않아도 된다. 코디네이터가 다음에 보드 도구를 쓰면 안내를 읽으라는 알림을 받고, 읽으면 화면 안내가 사라진다.
- 교체와 `/clear`는 계약 번호가 호환되지 않게 바뀐 경우의 마지막 수단으로만 남는다. 그때도 화면은 맥락을 덜 잃는 순서(그대로 두기, 대화 압축, 교체 또는 `/clear`)로 안내한다.

## 영향받는 사람과 화면

- 보드를 업데이트하는 사용자: 업데이트 뒤에 코디네이터를 교체하지 않는다. 화면 맨 위 안내의 문구와 순서가 바뀐다.
- 코디네이터 대화: 도구가 두 개 늘어난다. 기존 도구 일곱 개의 설명, 입력 형식, 결과는 그대로다.
- 기여자: 코디네이터 도구의 이름이나 입력 형식을 고치면 시험이 실패한다. 새 항목은 확장 길로 낸다.

## 제약

- 보드는 사람이 쓰지 않은 글을 출처 없이 보내지 않는다. `/clear`와 `/compact`를 대신 입력하지 않고, 세션을 다시 띄우지 않는다. 새 전송 경로를 만들지 않는다.
- 기존 도구 일곱 개는 같은 입력에 같은 결과를 낸다. 옛 정의를 가진 대화의 호출이 지금처럼 동작한다.
- 판단할 수 없으면 알리지 않는다(다른 실행기, 대화 ID를 읽지 못한 경우). Claude Code 프로필(다른 계정 등)로 도는 코디네이터는 Claude Code로 판정한다.

## 하지 않을 것

- 보드가 코디네이터 대화를 압축하거나 새로 시작하는 일.
- 기존 도구의 입력 형식 변경과 결과 형식 변경.
- Claude Code가 아닌 실행기의 대화에 대한 판정. 지금처럼 알리지 않는다.
- 버전 올리기(릴리스 PR에서 한다).

## 버린 대안

- **도구 설명을 짧게 줄이고 자세한 사용법을 안내 도구로 옮기기.** 처음에 이렇게 구현했다가 되돌렸다. 지문이 설명을 보지 않게 된 뒤에는 설명을 고쳐도 운영 대화에 알림이 생기지 않으므로 줄일 이유가 없고, 줄이면 안내를 읽지 않은 새 대화가 세부 규칙을 놓친다.
- **기존 도구마다 열린 `options` 객체 넣기.** 도구 일곱 개의 입력 형식을 모두 바꿔야 하고, 같은 항목을 넣을 자리가 둘이 된다(원래 자리와 `options`). 새 기능이 기존 도구에 속하지 않을 때 쓸 길도 따로 필요하다.
- **옛 정의에 없는 항목을 기존 도구에 그대로 보내라고 안내하기.** 확인한 대로 클라이언트는 막지 않지만, 대화가 가진 정의가 추가 항목을 금지하고 있어 모델이 따르지 않을 수 있고, 다른 실행기에서는 막힐 수 있다. 열린 입력을 가진 도구를 거치면 어느 쪽에서도 정의를 어기지 않는다.
- **지문에서 설명만 빼기.** 설명 변경으로 뜨는 안내는 없어지지만, 선택 항목을 더할 때마다 여전히 교체를 요구한다.
- **업데이트 때 보드가 `/compact`를 보내기.** 보드가 만든 글을 사람의 말처럼 보내는 일이라 금지 규칙에 걸린다.

## 성공 기준

- 설명 문구만 바꾼 빌드에서 운영 대화에 화면 안내와 도구 알림이 뜨지 않는다.
- 옛 정의를 가진 대화가 `board_action`으로 경로 출처 항목을 넣어 작업을 배정할 수 있다.
- 이번 업데이트 전의 대화가 교체, `/clear`, 압축 없이 안내 도구를 읽고 나면 화면 안내가 사라진다.
- 도구 알림은 같은 안내 내용에 대해 대화당 한 번만 붙는다.
- 코디네이터 도구의 이름이나 입력 형식을 계약 번호를 올리지 않고 바꾸면 시험이 실패한다.

## spec에서 정할 것

- 계약에 들어가는 것과 지문의 범위.
- 두 도구의 입력 형식, 검사 실패 때의 응답.
- 대화가 가진 계약 번호를 보드가 아는 방법.
- 알림을 붙이는 조건과 횟수.
